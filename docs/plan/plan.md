## 2026-09-28 Memos 00_Inbox、图片附件与自动投递修订

状态：待用户确认后实施。本节替代此前“每条 Memo 必须手动点击投递”和 `Memos/` 子目录约定；不改变 Echo/Ignis 自身的手动上传规则。

### 目标行为

1. Memos 新投递的正文保存到 GitHub 仓库的 `00_Inbox/`，文件名为上海时间 `yyyyMMdd-HHmmss.md`。已经存在的 `Memos/*.md` 历史文件不移动、不重命名。
2. Memo 关联的图片随正文作为同一个 Git commit 投递。图片保存到稳定的 `attachments/memos/{memoUID}/{sha256}.{ext}`，Markdown 中使用相对路径 `![](attachments/memos/...)`，保证 GitHub 与 Obsidian 都能正确显示。
3. 用户在 Memos 完成原生保存后自动创建不可变投递快照，不再要求逐条点击“投递到 Obsidian”。保存失败、空正文、仍在编辑的草稿不会触发投递。
4. 优化 Memo 编辑入口与操作栏：双击正文进入编辑；编辑器同时提供“暂存”和“保存”。暂存只保存在当前设备，不上传 Memos、Echo 或 GitHub；保存才写入 Memos 并自动投递。

### 实施设计

1. **收件箱路径**：Memos bridge 生成 `00_Inbox/` 候选名；Echo bundle 校验、同秒顺延分配、幂等记录和测试统一接受该目录 Markdown。目录已有同名文件时不得覆盖，按秒顺延重新分配；远端文件被电脑修改或移动后，后续版本继续进入冲突状态。
2. **附件快照**：服务端在事务外只读取已经与该 Memo 关联且保存完成的附件，通过现有存储层取得字节、MIME 与文件名；只接受可验证的普通文件，不读取外部 URL。正文和所有附件先计算 SHA-256，再一次性提交 Echo bundle。
3. **图片重写**：解析 Memos 正文中的附件引用，只重写确实属于当前 Memo 的图片为仓库相对路径。路径扩展名由经校验的 MIME/原文件名决定；相同哈希复用稳定路径。无法读取、摘要不符或引用归属不明时整次投递失败并保留 Memo，不生成缺图 Markdown。
4. **自动触发**：成功 CreateMemo/UpdateMemo 后，由 Memos 服务端调度一次自动投递；同一 Memo 同一 `update_time` 只允许一个 submission。短时间连续保存由幂等 ID 合并，旧版本必须先验证后再投新版本。自动触发失败不得让原生保存失败，错误写入可查询的投递状态并由可靠队列重试。
5. **兼容入口**：保留菜单投递作为“立即重试/手动补投”入口，和自动投递复用同一幂等 submission，不产生重复提交。前端明确显示待投递、已验证、失败/冲突，不把 Memos 保存成功显示成 GitHub 成功。
6. **限制与安全**：沿用正文 256 KiB、单附件 10 MiB、附件合计 25 MiB、最多 100 个附件的现有边界；服务 token 只在后端。自动投递只作用于当前登录用户已成功保存的 Memo，不扫描或补传全部历史 Memo。
7. **清理边界**：本修订不自动删除 Memos 源 Memo、附件或 GitHub 文件。待状态持久化、编辑会话 fencing 和条件删除全部完成并单独验收后，再启用“核验后清理”。服务器 Echo 队列的已验证正文也先保留，避免在清理协议完成前丢失恢复依据。
8. **编辑与暂存交互**：Memo 正文支持双击进入编辑，同时保留原有菜单编辑入口。编辑栏新增独立“暂存”按钮，按 `instance + user + memoUID` 将正文和待处理图片引用写入设备 `localStorage`，不调用 CreateMemo/UpdateMemo、附件上传或 Echo bridge；现有 Memo 也允许设备暂存。重新进入编辑时先比较草稿基线版本与服务端 `update_time`，版本不一致时提示选择，不静默覆盖。
9. **保存操作**：现有含义不清的保存图标改为明确的保存按钮/图标与可访问标签，移动端触控区域至少 44px。保存时先执行 Memos 原生正文和附件保存；全部成功后清除对应设备草稿，并由服务端自动投递该已保存版本。保存失败时保留草稿且不投递，界面不得显示成功。
10. **事件边界**：单击正文继续用于选择文本、打开链接和常规浏览，只有双击正文空白/文本区域进入编辑；按钮、链接、代码块、任务框、图片和移动端滚动手势不触发双击编辑。手机无可靠双击时继续使用菜单编辑入口，避免破坏原生触控行为。

3. 点击投递提交当前编辑器完整快照，等待中文输入法组合结束，明确包含哪些附件。服务端可靠落盘后才显示「已入队」；超时使用同一幂等标识查询或重试，不产生第二条笔记。
4. 图片选择先作为设备待提交内容；上传正文或附件必须由显式操作触发。空白无附件笔记不落盘；纯附件笔记视为有效内容。未完成的附件不能被误报为完整投递。
5. 区分「设备草稿」「服务器暂存」「已入队」「GitHub 已核验」「待结束编辑」「失败/需处理」。没有电脑回执不显示「电脑已收到」。
6. 后续编辑生成新版本，必须再次点击投递；旧快照可继续完成，但不得清理新版本。清理后编辑旧草稿时，提供显式另存新笔记，不自动复活原笔记。
7. 手机浏览器与输入法尚未指定，先覆盖 Chromium/WebKit 手机视口，再由用户实际手机验收；不以模拟视口替代真机输入体验。

### 3. 架构、接口与数据职责

采用固定上游版本加最小前后端补丁，Memos 与 Echo 独立进程/容器。服务间走受限通道，不直接读取或跨进程修改 Memos 数据库。Memos 的创建、编辑、附件变更与清理必须由同一服务端版本协议协调；未受保护的写入入口不得绕过协议。

逻辑接口在阶段一细化并测试，以下不是已存在的上游接口：
- 提交快照：认证用户、实例/笔记标识、幂等请求 ID、预期版本、正文和附件清单；返回稳定的 submission ID 与版本摘要。
- 查询状态：按用户权限返回提交状态、已核验版本与冲突原因，不返回凭据。
- 编辑会话：打开编辑器先取得会话标识和 fencing token；心跳只续会话，结束会话显式释放。旧 token 的写入被拒绝，设备草稿仍可恢复。
- 条件清理：提交已核验凭证及预期版本，由 Memos 服务端在事务/等效原子机制中同时检查版本、会话、退休状态后推进清理，不使用无条件 DELETE 拼接查询实现。

提交记录至少包括：实例与笔记稳定标识、提交 ID、单调版本、正文摘要、附件清单摘要、目标路径、预期远端 blob、GitHub attempt/commit、重试状态。不可用秒级更新时间作为唯一版本。设备会话记录与投递状态分离；清理后只留不含正文/附件的必要去重与退休元数据。

队列以显式提交记录为权威，分页扫描未完成提交用于恢复；不扫描普通笔记然后默认授权上传。先轮询恢复可靠队列，后续 Webhook 只做唤醒加速，不能依赖 webhook 唯一投递。重复、乱序与漏事件均应可恢复。

### 4. Markdown、附件与 GitHub 策略

- 一条笔记对应一个稳定路径，建议 Memos/yyyyMMdd-HHmmss.md，上海时区；同秒冲突用现有递增秒数分配方式，真实创建时间放元数据，路径首次分配后不随编辑改变。Memos/ 仅由接入程序创建新内容，不删除用户整理后的内容。
- 附件建议 attachments/memos/<稳定笔记标识>/<内容摘要>.<校验后扩展名>；文件名与路径由程序生成，拒绝路径穿越。Markdown 使用相对附件链接，不依赖登录态或临时远程地址。
- 元数据保存来源标识、创建时间和提交版本。标签保留正文语义；首期只承诺 Markdown 正文与已关联附件，不默默丢弃评论/关系等额外信息，发现未覆盖类型时提示其不在投递范围。
- 扩展 GitHubRemote 为正文及附件单个提交写入，同时保留 Echo 原单文件接口兼容。对每个预期文件核验指定提交中的 blob/内容；二进制使用字节摘要，不能按 UTF-8 文本核验。
- 首期拟限正文 256 KiB、单附件 10 MiB、单次附件合计 25 MiB；阶段一实测资源后固定在接口和 UI，超限明确拒绝并保留草稿，不隐式截断或自动接入 LFS。
- 远端文件被修改、移动或删除后进入冲突，不覆盖、不复活；用户可显式另存。并行 Echo 提交产生分支冲突时重新读取并安全重试，禁止强推。
- 同一提交丢回执或进程重启时恢复持久 attempt，避免重复提交。GitHub 与服务器不能做跨系统事务，必须采用可重试状态转换与核验补偿。

### 5. 自动清理是独立验收关卡

清理必须同时满足：该快照正文和全部附件已核验到 GitHub；当前源版本仍匹配；没有未提交的新正文/附件；所有编辑会话已明确安全结束；距最后活动超过 120 秒；没有未解决错误。

特别约束：心跳过期只能说明连接状态未知，不能证明用户结束编辑。失联、手机后台休眠或服务重启造成会话不确定时，禁止自动清理；等待恢复会话明确释放或用户处理。阶段一需实现不含正文的持久会话/不确定状态，避免重启把所有会话当成关闭。打开编辑和开始清理需互斥；迟到请求用 fencing token 拒绝。仅在接入程序加锁无法约束 Memos 原生写入，不算通过。

清理顺序：原子校验并标记退休 → 可恢复地删除正文与自有附件 → 核验完成 → 清掉投递快照副本，仅留元数据。故障时可续跑，不恢复已退休源记录。共享附件必须核查引用，禁止连带删除其他笔记内容；不传播删除到 GitHub/电脑。

清理范围包括 Memos 数据库、附件存储、Echo 队列、临时下载与应用缓存；日志不记录正文。归档不等于清理。数据库 WAL、空闲页及备份的残留与保留周期须单独核实，不能把逻辑删除宣传为安全擦除。不对临时正文做无限期快照备份；失败与未投递内容不得按年龄清除，应告警请求处理。

若无法在固定版本中落实上述原子检查与会话保护，停止自动清理阶段，仅保留合成数据验证结果，不以「延迟更久再 DELETE」替代，也不以默认长期留存真实内容绕过用户要求。

### 6. 目录、配置与上游维护

以下目录仅在计划确认和阶段一选型后创建：
- upstream/memos/：固定上游源码与许可证、本地补丁和来源说明；不保留嵌套 Git 历史，不含数据库、凭据、构建产物。先记录 tag、commit 与构建工具链，升级必须重跑协议与清理测试。
- src/server/memos/：接入适配、状态转换与恢复逻辑；保持 Echo 现有接口可用，不引入通用工作流平台。
- tests/memos/：合成测试数据、契约/并发/恢复用例；运行产物写系统临时目录，按授权清理，不误删工作区文件。
- deploy/memos/：不含凭据的容器与配置模板；运行数据路径必须在项目外独立目录。部署域名、资源限额和存储位置在部署审批前确定。
- docs/setup/memos.md：固定版本、启动方法、验证证据、运维与回退说明；本轮尚不创建。

新增入口建议使用 Memos 原生登录、私有可见性、关闭开放注册和公开分享；这是待确认的新增服务策略，不恢复 Echo 已取消的网页登录鉴权。保留 HTTPS、Host、同源写入与适用的 WebSocket Origin 校验。GitHub token 仅由服务端使用；服务间凭据另设最小权限，不向浏览器下发。新增投递及清理开关默认关闭，不能因 Echo 当前已开启同步而自动启用 Memos。

## 2026-09-30 旧笔记续写与 Obsidian 反链

### 目标

把“编辑已经投递到 GitHub 的旧笔记”改为续写流程：Memos 创建一条新笔记，新笔记在投递生成的 Markdown 中引用旧笔记；旧 Markdown 不改写。Obsidian 解析新笔记中的 WikiLink 后，在旧笔记的反向链接面板中自动显示新笔记，由一条显式正向链接形成可双向浏览的关系。

本次只规划 Memos → Echo → GitHub → Obsidian 现有链路上的增量能力。继续使用 `00_Inbox`、现有附件路径、自动投递、GitHub 核验和临时中转规则，不引入新的长期数据库或独立前端。

### 用户交互

1. 已核验投递成功的笔记不再通过默认编辑入口原地改写。双击正文或选择“续写”时，打开一个新的编辑器，并显示“续写自：<原笔记时间>”。
2. 新编辑器保存后创建新的 Memos memo，并按现有规则自动投递；原 memo 和原 GitHub 文件均保持不变。
3. 尚未投递、投递失败或只存在于设备草稿中的笔记仍允许原地编辑，避免为尚未形成历史版本的内容制造无意义分支。
4. 续写笔记在 Memos 中显示原生关系标识，可返回原笔记；GitHub Markdown 中显示 Obsidian 链接。浏览器不计算仓库路径，也不接触 bridge token。
5. 第一版只支持一个直接上游。对续写笔记再次续写会自然形成链：A ← B ← C；Obsidian 仍可沿链接和反链浏览全部版本。

状态规则：

| 原笔记状态 | 双击/编辑行为 | 续写保存行为 |
| --- | --- | --- |
| 设备草稿 | 编辑原草稿 | 暂存到 localStorage |
| 未上传或上传失败 | 编辑原 memo | 重新按现有链路投递 |
| 已入队但未核验 | 禁止形成依赖，提示等待投递完成 | 不创建可能失效的链接 |
| 已核验投递 | 新建续写 memo | 自动投递新的 Markdown |

### 链接格式与稳定性

续写内容投递后在正文末尾追加：

```markdown

---
续写自：[[20260930-142600]]
```

链接使用已核验投递文件的实际文件名，不带 `.md` 和目录。时间只用于示例，服务端必须读取队列中已经分配并核验的真实路径，不能根据 memo 创建时间重新推算。使用文件名链接后，用户把旧笔记从 `00_Inbox` 移到 Vault 其他目录时，Obsidian 仍可解析链接；现有文件名分配机制负责避免重名。若检测到无法唯一确定的历史文件名，续写投递进入可重试失败状态，不静默指向错误文件。

Markdown 中只写一条正向 WikiLink。所谓“双链”由 Obsidian 基于该链接生成反向链接；不为此修改旧文件，也不产生第二次 GitHub 提交。

### 数据与接口设计

1. **Memos 原生关系**：创建续写 memo 时通过现有 memo relation API 保存对子 memo 与父 memo 的引用关系，优先使用 `REFERENCE` 语义；不把 GitHub 路径写进用户正文。
2. **Bridge 快照**：扩展 Memos bridge 的服务端快照，传递父 memo 的稳定标识和关系类型。服务端继续核验当前登录用户、子 memo 所有权和父 memo 所有权，拒绝跨用户引用。
3. **Echo 权威解析**：Echo 依据 `(instance, owner, parent memo)` 查询父笔记的持久化投递记录，只接受 `verified` 状态及其中的实际 `assignedPath`。浏览器提交的任何路径仅作无效输入处理。
4. **持久化依赖**：把父 memo 标识及解析出的父文件名写入子任务记录，使进程重启、Memos 临时正文清理或父 memo 后续不可访问时仍能安全重试。现有 JSON 队列扩展字段即可，不安排数据库迁移。
5. **Bundle 生成**：在正文和附件快照完成后，由 Echo bundle 层追加标准化续写区块。附件与 Markdown 仍在同一个 GitHub 提交中投递。
6. **投递状态**：若父笔记尚未核验，子任务进入明确的 `waiting_parent` 状态；父任务核验成功后自动唤醒。父任务永久失败、归属不符或历史映射歧义时，子任务保留且展示原因，不生成断链文件。
7. **幂等键**：子 memo ID、子版本和父关系共同参与修订识别；相同修订重试复用候选路径和父映射，不重复创建 Markdown 或 GitHub 提交。关系变化视为新修订，但已核验的历史文件不原地改写。

### 安全与清理约束

- 旧笔记一旦作为父节点被核验，不因创建续写而更新或删除其 GitHub 文件。
- Memos 临时正文清理必须等待该 memo 自身投递核验和活动会话失活；父子关系元数据及 Echo 投递映射保留到现有队列清理周期结束。
- 父 memo 失联不等于关系失效。只要 Echo 已持久化其核验路径，后续续写可以使用该映射。
- 续写功能默认以功能开关关闭；先用合成 memo 和测试仓库验证。真实内容投递、生产部署及任何数据库迁移继续按项目规则单独授权。
- 不修改 Echo 免登录策略，不向浏览器暴露 GitHub、Echo bridge 或服务器凭据。

### 实施范围

预计涉及以下模块；实施前在 `docs/todo/todo.md` 拆分任务：

1. Memos 前端：新增“续写”入口、已投递状态下的双击行为、父关系提示和等待/失败状态。
2. Memos 服务端 bridge：读取并核验 memo relation，扩展提交快照。
3. Echo Memos 模型与队列：保存父依赖、查询已核验父路径、处理 `waiting_parent` 与恢复唤醒。
4. Echo bundle：生成规范化 WikiLink，保证正文、链接和附件顺序稳定。
5. 状态接口：让前端区分未投递、处理中、已核验和等待父笔记。
6. 文档：更新数据契约、生产配置、验证记录和回滚方法。

不包含：修改旧 GitHub Markdown 来写入显式反向链接；扫描或克隆完整笔记仓库；自动重命名历史文件；支持多个父节点；把私人笔记或测试凭据提交到应用仓库。

### 实施顺序

1. 先补充数据契约和队列兼容读取，确保旧任务在新增字段缺失时仍可运行。
2. 实现父投递映射查询、等待状态、唤醒与 bundle WikiLink，并完成服务端单元/集成测试。
3. 接入 Memos 原生 relation 和 bridge 所有权校验，验证浏览器无法伪造父路径。
4. 接入原版 Memos 界面的续写交互，保持现有暂存、保存、附件与自动投递行为。
5. 使用合成数据完成 Memos → Echo → 测试 GitHub → 本地 Obsidian 全链路验收。
6. 验收后再申请生产部署与一组真实笔记验证授权；确认正常后逐步启用功能开关。

### 验收标准

- 已核验旧笔记执行续写后，只新增一个子 Markdown，旧 Markdown 的 blob 内容不变。
- 子 Markdown 正文末尾恰有一个指向父文件实际 basename 的 WikiLink；Obsidian 点击可打开父笔记，父笔记反链面板可看到子笔记。
- 父路径发生过候选冲突时，链接采用最终核验路径，不采用创建时间推算值。
- 父笔记未核验时不产生断链提交；父笔记核验后，等待中的子任务自动继续。
- 服务重启和重复请求不产生重复文件、重复附件或重复 GitHub 提交。
- 含图片的续写笔记在同一提交中正确投递，图片展示和父链接均有效。
- 跨用户父关系、伪造路径、已删除或歧义映射均被拒绝并保留可诊断状态。
- 手机网页双击已投递笔记会进入续写，新笔记保存后自动投递；草稿和失败笔记仍可原地编辑。
- 现有非续写笔记、Echo/Ignis、WebSocket、Host/Origin 校验和清理保护测试全部通过。

### 回滚

关闭续写功能开关即可恢复现有编辑与投递路径；新增队列字段由兼容读取忽略，无需数据库回滚。已经生成的续写 Markdown 是普通 Markdown 与 WikiLink，回滚后仍能在 Obsidian 中正常使用，不删除或改写。
## 2026-09-30 Memos 手机按钮与图标对齐修订

### 已确认问题

1. 编辑器底栏在 320px 宽度下同时放置插入、可见性、暂存和保存控件；两个操作按钮各自固定 `min-w-24`，左右分组不换行且按钮基类全局 `shrink-0`，总宽度超过编辑器内容区后会挤压或溢出，图标随之偏离预期位置。

4. 格式工具栏虽然会根据容器宽度折叠命令，但其紧凑按钮仍沿用桌面尺寸；编辑器底栏则没有等价的窄屏布局规则。

## 2026-09-30 Memos 附件时间戳命名与 Obsidian 路径修复

### 目标

- Memos 投递到 Echo/GitHub 后，附件文件使用可读且稳定的上海时间戳名称，不再暴露 64 位内容摘要作为文件名。
- 导出的 Markdown 只保留 Obsidian 可解析的新附件路径，彻底移除 Memos 的 `/file/attachments/...` 地址，避免同时出现一个失效图片和一个可用图片。

### 已定位原因

- 当前 bridge 用附件 SHA-256 作为 GitHub 文件名，虽能保证唯一性，但电脑端文件名不可读。
- 路径替换只覆盖“UID + 当前文件名”的少数精确字符串；Memos 还可能生成省略文件名、带查询参数、绝对 URL 或不同转义形式的 `/file/attachments/{uid}`。未命中的旧地址会保留，bridge 随后又追加正确路径，形成一坏一好的两个图片引用。

### 实施范围

1. 将 bridge 附件快照补充附件创建时间；GitHub 路径改为 `attachments/memos/<memo-uid>/yyyyMMdd-HHmmss[-NN].ext`。同一秒同扩展名按稳定顺序增加两位序号；历史已投递文件不迁移、不删除。
2. 按附件 UID 识别并替换相对或同实例绝对的 Memos 托管附件 URL，兼容有/无文件名、URL 转义与查询参数；每个附件最终只生成一个 Obsidian 引用。
3. Echo bundle 校验同时接受新的时间戳附件路径和历史摘要路径，保证旧队列可恢复、重试和核验。
4. 增加多附件同秒命名、旧 URL 变体、无重复引用、历史 bundle 兼容及非法路径拒绝测试。

### 约束与验收

- 时间戳使用附件自身 `CreatedTs` 的 Asia/Shanghai 时间，重试和 memo 更新不改变已分配名称。
- 不修改 Memos 数据库中的原始附件名，不迁移或删除 GitHub 已存在的历史附件。
- 生成的 Markdown 不含 `/file/attachments/`；bundle 中每个引用都对应同一次 Git commit 内的实际附件。
- Go 定向测试、Echo 测试、Memos lint/build、差异检查和 ss-review 通过后，按用户最新授权自动提交、推送并部署。
